# Plano: App C2S — Padronizador & Validador de Planilhas de Leads

## Situação atual do diretório
Existe um esqueleto Next.js 14 (App Router + TS + Tailwind) com a camada `src/lib` **já implementada e boa** (`schema.ts`, `normalize.ts`, `spreadsheet.ts`). Porém **faltam UI, layout e o fluxo de PDF**, e há 3 correções de alinhamento:

1. **Paleta errada**: Tailwind atual é `moss/clay/bark`. Precisa virar **Slate + Esmeralda** (sua escolha).
2. **PDF engine errado**: `package.json` traz `pdf-parse` (server-side). Você escolheu **pdf.js client-side**. Trocar.
3. **Bug em `normalize.ts`**: usa um campo `columns` que não existe na `ReportItem` interface, mascarado por `as ReportItem`. Pequena limpeza.
4. **Sem `app/`**: faltam `layout.tsx`, `page.tsx`, `globals.css`. A pasta `app/api/pdf/` (vazia) sai.

## Decisões já tomadas
- Stack: Next.js 14 App Router + TS + Tailwind (já montado).
- Paleta: **Slate (base neutra) + Esmeralda (accent de ação)**.
- PDF: **100% client-side via pdf.js** (`pdfjs-dist`); dados nunca saem do navegador.
- Planilhas: `xlsx` (SheetJS) já presente — reaproveitar.
- Sem backend, sem persistência, sem `api/pdf`.

## Riscos / observações
- **pdf.js worker no Next**: usar `new Worker(new URL('pdfjs-dist/build/pdf.worker.min.mjs', import.meta.url))` (webpack 5). Se houver conflito, fallback `GlobalWorkerOptions.workerSrc` apontando para `/public`. É o ponto de maior incerteza técnica — por isso o fluxo tem **fallback de revisão manual** quando o PDF é ambíguo, como o briefing pediu.
- Inter/Fraunces via `next/font/google`; se offline em build, cai em `system-ui`/`Georgia` (aceitável).
